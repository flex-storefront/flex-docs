Flex Storefront implements a comprehensive error handling system that manages both expected and unexpected errors. The architecture follows the repository pattern, allowing for flexible service provider integration while maintaining a clean separation of concerns.

## Architecture

### Error Repository
The error repository pattern is implemented separately from [user interaction logging](../../analytics/51-analytics-overview) for several key reasons:

- **Separation of Concerns**: Error logging often requires different service providers and configuration than user analytics
- **Different Data Models**: Error logs contain stack traces and technical details, while user interactions focus on business metrics
- **Compliance Requirements**: Error logs may contain sensitive information requiring different handling than analytics data
- **Performance Consideration**: Error logging shouldn't impact normal analytics collection and vice versa


### Error Handler Widgets

Error handler widgets serves as a widget-level error boundaries, capturing errors that occur within its widget subtree. For example, `FullPageError` displays a full-page error screen. More information may be found [here](../65-displaying-errors).


### BlocObserver Integration

The custom `AppBlocObserver` extends Flutter Bloc's `BlocObserver` to provide error handling for state management:

- Error Tracking: Captures and logs errors that occur during state transitions
- State Validation: Ensures state changes follow expected patterns
- Performance Monitoring: Tracks bloc lifecycle events for debugging
- Crash Prevention: Catches and handles errors before they propagate to the UI


```dart
@override
void onError(BlocBase<dynamic> bloc, Object error, StackTrace stackTrace) {
  if (_printError) {
    _printOutput(
      title: 'Error',
      subtitle: bloc.runtimeType.toString(),
      content: '$error\n$stackTrace',
    );
  }

  errorHandling.logError(
    code: error.toString(),
    timestamp: DateTime.now(),
    additionalContext: {'\nstacktrace': stackTrace},
  );

  super.onError(bloc, error, stackTrace);
}
```

Flex Storefront is able to deal errors both expected and unexpected. Expected errors utilize the [repository pattern](https://www.geeksforgeeks.org/repository-design-pattern/) to allow for the switching of service providers for error logging, whereas unexpected errors are, by default, funnled to Firebase Crashlytics. Details on the handling of expected errors may be found within [FlexError](../63-flex-error); details pertaining to unexpected errors may be found within [Unhandled Errors](../67-unhandled-errors).

## Crash Reporting

### Firebase Crashlytics Integration

Both error handlers report to Firebase Crashlytics, providing:
- Stack traces
- Error messages
- Fatal error flags
- Device information
- App state at time of crash





## Internationalization

Error messages are managed through the app's localization system. Ensure all error messages are defined in the appropriate translation files:

```dart
// i18n/strings.g.dart
common.errors.networkError: "Network connection error occurred"
common.errors.unknownError: "An unknown error occurred"
common.errors.anErrorOccured: "An error occurred"
```
